# 기기 업데이트

- 상태: 승인한 peer를 통한 개발 빌드 전달·자동 적용 구현
- 기준: `docs/product/02-spec.md`, `internal/peerupdate`, 관리 앱의 update controller

양쪽 기기를 명시적으로 페어링한 뒤, 받는 PC가 상대의 업데이트 수신을 허용해야 한다.
입력 제어 권한과는 별도이며 철회할 수 있다. 송신자는 UI의 ‘업데이트 보내기’ 또는
`krasis-cli update send ALIAS`로 현재 배포 폴더를 전달한다.

관리 채널은 기존 인증서를 pin한 mTLS와 현재 trust를 확인한다. 묶음의 manifest,
generation/revision, SHA-256 및 파일 구성을 검증해 별도 폴더에 저장한다. 관리 앱의
자동 적용은 입력 연결을 안전하게 끝내고 새 UI와 agent를 시작한다. 이전 파일과
페어링 정보는 보존한다. 받는 PC의 관리 앱은 창 또는 트레이에서 실행 중이어야 한다.
에이전트도 종료됐다면 원격 명령을 받을 수 없으므로 해당 PC의 고정 복구 CLI를 사용한다.

작업 공간에서 상대 기기를 고른 뒤 ‘상대 앱 열기’를 누르면 기존 관리 채널로
상대의 마지막 검증된 Krasis 실행 파일을 연다. 입력 연결을 해제한 상태에서도
사용할 수 있다. 상대의 입력 제어 허용을 확인하며 실행 경로나 명령을 전달하지 않는다.
요청은 한 번만 보내고 같은 요청의 응답을 확인한다. 실행 요청 수락과 실제 창 표시를
구분하며, 상대 에이전트도 종료됐다면 응답을 받을 수 없다.
`window_ready`는 검증한 상대 UI 프로세스가 창 준비를 보고한 상태다.
`launch_accepted`는 실행 작업 수락, `launch_requested`는 실행 요청 성공이다.
두 상태에서는 같은 요청을 계속 조회하고, 창 준비를 확인하지 못하면
`window_unconfirmed`로 표시한다. 관리 화면을 다시 열어도 진행 중인 요청 ID로만 조회한다.
자동 시작을 켠 상대에서는 로컬 예약 작업이 종료된 에이전트를 복구한 뒤 다시 요청할 수 있다.
g189부터 응답이 없는 요청은 20초 후 `peer_unresponsive`로 끝내고 더 이상 전달하지 않는다.
이 결과만으로 상대 앱의 종료 여부를 단정하지 않는다. 수락 응답 이후 창 준비 확인은
요청 시작부터 최대 1분까지 계속하며, 화면에도 ‘상대 앱을 여는 중’으로 전환한다.
g190에서 앱 열기와 `/v2/status`는 파일·클립보드·진단 전송과 별도의 HTTP client,
worker와 서버 gate를 사용한다. 느린 실행 작업도 `launch_accepted`를 먼저 응답하며,
완료 결과를 같은 요청 ID로 조회한다. 상대가 반환한 `busy`는 거부 결과이고 로컬 조회
경합인 `query_busy`만 계속 조회한다. 창을 다시 표시하거나 에이전트가 바뀌면 UI 준비를
다시 보고한다. 예약 복구는 g188 이상을 상대 PC에서
한 번 실행해 자동 시작을 등록해야 작동하며, g186 에이전트가 꺼진 상태를 원격에서 복구하지는 못한다.

`queued`는 시작, `DELIVERED`는 수신 확인, `UPDATED`는 상대의 정확한 새 agent 빌드
관측이다. 수신과 적용 완료를 동일시하지 않는다. `update wait ALIAS ID`는 작업 ID를
고정해 적용 확인 또는 실패까지 기다린다. 확인이 끊기면 자동으로 다시 전송하지 않는다.
g190에서 peer 업데이트의 APPLYING 예약은 5분 뒤 같은 ID·peer가 여전히 적용 중일
때만 실패로 종료하고 잠금을 해제한다. 공개 배포의 3분 예약과는 별개다.

개발 EXE의 checksum 검증은 배포자 코드 서명이 아니다. 공개 배포 경로는 아래의
별도 배포 서명을 확인한다. 실제 외부 배포는 release policy의 승인 조건을 따른다.
g140부터 이미 설치한 보호 입력의 갱신도 새 버전 시작 과정에 포함된다. 해당 PC의
Windows 관리자 확인은 자동 승인하지 않는다. 취소하면 일반 입력으로 앱을 열고,
화면의 보호 입력 갱신 버튼으로 다시 요청할 수 있다. 최초 설치·불확실한 설치 상태를
자동 갱신으로 처리하지 않으며, 설치 결과가 미확인이면 agent 시작을 보류한다.
g190은 PENDING 설치 결과를 다시 확인하지만 관리자 동의창을 자동으로 다시 열지 않는다.
같은 generation의 다른 revision 에이전트는 불일치로 거부하고 실행 중인 프로세스를 유지한다.
새 버전 앱이 기존 창에 전달되면 전체 묶음을 검증·저장하고 연결과 페어링이 끝난 뒤
교체한다. 대기 중에는 제목에 ‘새 버전 대기’를 표시한다.

고정 복구 경로는 에이전트 시작 확인 뒤 갱신한다. 실패한 새 버전이 정상 복구 경로를
덮어쓰지 않으며 이전 실행 기록은 `launch/previous.json`에 보존한다. 자동 시작 상태는
등록값과 실제 예약 작업을 대조한다. 자동 업데이트 옵션만 바꾸면 시작 등록은 건드리지 않는다.
`krasis-cli app recovery-status --json`으로 예약 작업과 마지막 자동 복구 결과를 확인한다.
g191부터 설정·재연결 대상·복구 일시 중지 상태 조회는 읽기 전용으로 폴더를 연다.
예약 CLI가 고정 복구 폴더에서 실행 중이어도 삭제 권한을 요청하지 않으므로 설정
읽기의 공유 충돌을 피한다. 파일이 없으면 기본값을 반환하며 조회만으로 폴더를 만들지 않는다.
파일 ACL·링크·크기·JSON 검증은 유지한다.
g192부터 1분 주기의 예약 복구는 기록된 GUI `krasis.exe --background-recovery`로
실행한다. 기존 콘솔형 CLI 직접 실행은 최초 g192 실행 때 같은 사용자 소유의 작업에
한해서 전환한다. 자동 복구는 창·트레이·renderer를 만들지 않고 기존 `app ensure`
동작과 진단 receipt를 사용한다. 정상 에이전트가 있으면 종료하고, 없을 때만 마지막
검증된 앱을 연다. 터미널용 `krasis-cli.exe`의 출력과 실행 방식은 유지한다.
새 버전의 실행 기록을 갱신하면 예약 작업 경로도 맞추며, 이전 실행 기록과 일치하는
기존 경로만 변경한다. 다른 실행 파일·인자·소유자·권한의 예약 작업은 덮어쓰지 않는다.

진단에는 버전·집계 상태·실패 코드만 사용하며 raw 입력, PIN, clipboard 내용과
peer 주소를 기록하지 않는다. 설치·자동 적용의 실기기 증거와 외부 배포 승인은
각각 기록한다.

## 공개 배포 자동 업데이트

앱 아래쪽 ‘자동 업데이트’는 기본으로 켜져 있다. 시작 1분 후와 이후 6시간마다
GitHub의 `releases/latest/download/latest.json`을 확인한다. ‘업데이트 확인’으로
즉시 확인할 수 있다. 옵션을 끄면 주기 확인·다운로드·자동 적용을 멈춘다.
수동 확인은 새 버전의 존재만 확인한다.
확인·다운로드 실패 시 1분·5분·15분·6시간 간격으로 재시도한다. READY 묶음이 있으면
피드 확인 실패에도 보존하고, 더 새 버전이 있는지는 계속 확인한다.

피드는 Ed25519로 서명한 base64 payload와 signature다. payload에는 generation,
revision, Windows 플랫폼, ZIP 주소·크기·SHA-256을 담는다. 빌드에 내장한 공개키로
서명을 검증하고, 고정 GitHub 저장소의 새 generation만 받는다. 다운로드 후 기존
updatebundle 검증·별도 폴더 저장·앱/에이전트 교체를 재사용한다.

연결 중에는 다운로드까지만 진행한다. 연결과 페어링을 끝낸 뒤 자동으로 적용한다.
상대 PC가 없는 단독 설치에서도 적용할 수 있다. 인터넷 오류나 잘못된 서명은 현재
앱을 종료하지 않는다. peer 업데이트와 공개 업데이트의 적용은 같은 잠금으로 직렬화한다.
적용 직전 자동 업데이트 설정을 다시 확인하고, 에이전트의 같은 잠금에서 적용을
예약한다. 예약 이후 CLI 연결·페어링·다른 업데이트는 거부한다. 실행 실패 시 같은
요청 ID의 예약을 해제하며 관리 앱이 중단되면 3분 뒤 예약이 만료된다.

다운로드한 원본 ZIP과 서명된 피드를 사용자 전용 경로에 저장한다. 재실행할 때
서명·ZIP 해시·배포 메타데이터·스테이징 파일을 다시 대조한 뒤 READY를 복원한다.
같은 공개 업데이트는 같은 폴더를 재사용한다. 기록된 공개 업데이트의 오래된 폴더는
정리하되 최신 두 폴더, 실행 중인 UI·에이전트와 고정 복구 경로는 유지한다.
실행 중인 제품 프로세스의 경로를 확인하지 못하면 정리를 보류한다. 공개 배포 정리는
서명된 기록에 포함된 폴더만 대상으로 한다.

g190은 에이전트 시작 시 `updates` 바로 아래의 32자리 소문자 hex 폴더도 정리한다.
최근 두 폴더, 24시간 이내 폴더, 모든 세션의 실행 중인 제품 폴더, 현재·이전 복구 경로,
공개 배포 기록의 폴더와 READY·STAGED·APPLYING 폴더는 보존한다. 네트워크 worker가
시작됐거나 프로세스·기록 조회가 실패하면 삭제하지 않는다. 최대 1024개만 검사하며
링크·junction을 따라가지 않는다. 삭제 실패는 숨기지 않고 `doctor`와 새 진단의
`cleanup`/`cleanupIncomplete`에 남긴다. 파일 경로와 원본 오류는 진단에 포함하지 않는다.

배포 환경에는 `KRASIS_RELEASE_PUBLIC_KEY`(base64 Ed25519 공개키)와
`KRASIS_RELEASE_PRIVATE_KEY`(PKCS8 PEM 서명키)가 필요하다. 서명키는 GitHub release
환경의 Secret, 공개키는 Variable로 등록한다. 실제 키가 없으면 ‘공개 배포 준비 중’으로
표시하고 파일을 실행하지 않는다. 배포 서명은 Windows Authenticode 서명과 별개다.

깨끗한 커밋에서 `KRASIS_RELEASE_PUBLIC_KEY`를 설정하고 `scripts/build-workspace.ps1`로
만든 폴더를 `node scripts/sign-release.mjs dist/workspace/g숫자`에 전달한다.
서명기는 실제 EXE의 공개키 내장 여부·패키지 검증을 확인한 뒤 ZIP과 latest.json을 만든다.
GitHub release 워크플로는 승인된 기존 `g숫자` 태그를 수동 지정할 때만 실행한다.
평상시 push나 개발 빌드에서는 공개 릴리스를 만들지 않는다.
